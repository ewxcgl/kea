# KEA Wire Protocol v1

Normative spec. Both the Kotlin (Android) and Swift (iOS) clients implement this
document. The relay is deliberately dumb: it routes opaque blobs and knows
nothing about geography.

## 0. Design constraints

| Constraint | Consequence |
|---|---|
| Location is only transmitted **while someone is watching the map** | A `watching` boolean is *not* secret. It must be routed in clear. |
| Relay must never learn coordinates | All payloads are AEAD-sealed. The relay routes by `groupId` only. |
| A group member must not be able to forge another member's position | Payloads are **signed** per-device, not just group-encrypted. |
| A replayed old fix must not resurrect a stale position | Nonce = `(deviceId, sessionId, seq)` with a strictly increasing `seq`, plus a `ts` freshness window. |

## 1. Transport

- WebSocket only. TLS is mandatory (`wss://`). Plain `ws://` is refused in release builds.
- **Text frames** carry JSON: handshake, control, and routing.
- **Binary frames** carry sealed payloads, prefixed with a 3-byte routing header.

A member's public identity and its `watching` flag travel as cleartext control
frames inside the group. This is intentional and is the only metadata leak.

## 2. Identity

Each device generates at first launch and persists in the platform keystore:

| Key | Algorithm | Purpose |
|---|---|---|
| `signPriv` / `signPub` | Ed25519 | Authorship of payloads. Prevents impersonation. |
| `x25519Priv` / `x25519Pub` | X25519 | Wrapping the group key to a specific device. |

`deviceId` = base64url( `SHA-256(signPub)[0..8]` ) — 11 chars, human-typeable.
Stable across reinstalls only if the keystore survives; otherwise it is a new identity.

## 3. Group key

32 random bytes, generated by the group creator.

Delivery is via the invite link **fragment** (`#`), which browsers and chat apps
never transmit to any server:

```
kea://join#<base64url( joinPayload )>

joinPayload (CBOR-free, length-prefixed, see §8):
  version    u8   = 1
  groupId    16 random bytes
  groupKey   32 random bytes
  expiresAt  i64  unix seconds; 0 = never
  kdfSalt    16 bytes   (present only when a passphrase is set)
  kdfHash    8 bytes    (scrypt params, present only when a passphrase is set)
  wrappedKey 32 bytes   (present only when a passphrase is set)
```

Without a passphrase, `groupKey` sits in the fragment in the clear — anyone the
link is forwarded to can join **and** read history. The UI therefore requires
an explicit confirmation, and strongly suggests a passphrase.

With a passphrase, `groupKey` is wrapped with `scrypt(passphrase, kdfSalt, N, r, p)` →
32-byte key → XChaCha20-Poly1305 with a 24-byte nonce derived as
`HKDF-SHA256(scryptKey, kdfSalt, "kea-invite-v1", 24)`.

> **v1 tradeoff.** Membership changes rotate the group key. This revokes
> *future* traffic but not *past* traffic, since every member holds a plaintext
> copy of the key. Per-device key wrapping (`x25519`) is defined in the format
> above but only partially used in v1. See §11.

## 4. Payload sealing

Every payload is sealed identically on all platforms.

```
info      = "kea-payload-v1"
aad       = info || 0x00 || groupId(16) || deviceId(11 ascii) || sessionId(8) || seq(u32be) || ts(i64be) || typeTag(4)
key       = HKDF-SHA256(ikm = groupKey, salt = groupId, info = "kea-payload-v1", len = 32)
nonce     = HKDF-SHA256(ikm = groupKey, salt = groupId, info = "kea-nonce-v1" || deviceId || sessionId || seq, len = 12)
sealed    = ChaCha20Poly1305(key, nonce, plaintextJSON, aad)   // RFC 8439, 12-byte nonce
signature  = Ed25519(signPriv, 0x00 || aad || sealed)
```

Binding `typeTag` into the AAD means the AEAD authenticates it, so a signed
`LOC` cannot be replayed as a `FENC` even though the tag travels in cleartext.
`seal()` is authoritative for `seq` and `ts`: it overwrites any copies inside
the plaintext body, so a sender cannot smuggle a second unverified timestamp.

The **nonce travels with the ciphertext** on the wire as `nonce || sealed`,
not as a separate routing field. That is the "combined" layout that iOS
CryptoKit produces natively via `ChaChaPoly.SealedBox.combined`, and it is what
lets a single reference vector satisfy both platforms. Receivers must check the
carried nonce equals the derived one before decrypting.

Verify the Ed25519 signature **before** attempting decryption, and drop the frame
on failure. `seq` is a per-`(deviceId, sessionId)` counter starting at 0,
incrementing by one per sealed payload. A receiver rejects `seq <= lastSeenSeq`
for that session. `sessionId` is 8 random bytes regenerated on every app start,
so a restart legitimately resets `seq` to 0.

`ts` is unix **milliseconds** on the sender's clock. Receivers reject frames
older than `MAX_SKEW_MS` (default 10 minutes) to bound stale replay.

## 5. Relay framing

Routing header on binary frames — 3 bytes, big-endian:

```
  byte 0 : flags
           bit0 = 0x01  sealed payload
           bit1 = 0x02  ack requested
  byte 1-2: u16be payload length (max 16384)
```

Body, then `sealedBytes` from §4, verbatim. The relay **must not** parse or
validate it.

```
  deviceId     11 ascii
  sessionId     8
  seq           4  u32
  tsMs          8  i64
  typeTag       4  ascii, space padded
  nonce        12
  sealed       var  ChaCha20Poly1305 ciphertext || 16-byte Poly1305 tag
  signature    64  Ed25519
```

Fixed overhead is 135 bytes, so roughly 16.3 KB of the 16 KB cap is usable for
the sealed JSON. A `LOC` payload is ~140 bytes on the wire.

## 6. Control messages (cleartext JSON)

```jsonc
// client -> relay, first frame. No auth required: possession of groupId is
// the authorisation. This is a bearer-token model; see §11.
{ "t": "hello", "group": "<b64url 16B>", "dev": "<deviceId>",
  "name": "<display name>", "pk": "<b64url ed25519 pub>", "v": 1 }

// server -> group: a member's watch state changed. Drives the watch-gate.
{ "t": "watch", "dev": "<deviceId>", "on": true }

// server -> group: roster + presence, sent on join and every 10s
{ "t": "roster", "members": [ { "dev":"…", "name":"…", "pk":"…", "on":true,
                               "watching":false, "seen":1712345678901 } ] }

// client -> relay: request another member's live position for a bounded time
{ "t": "pull", "dev": "<deviceId>", "ttl": 900 }

// relay -> target: forwarded pull request
{ "t": "pullreq", "from": "<deviceId>", "ttl": 900 }

// server -> group: someone asked for a live position
{ "t": "pulled", "dev": "<target>", "by": "<requester>", "ttl": 900 }

// client -> relay
{ "t": "leave", "group": "<b64url 16B>", "dev": "<deviceId>" }
```

`on` is `watching`, i.e. "I have the map open and I want positions". `seen` is the
relay's last-contact timestamp in ms, used only to grey out stale members.

## 7. The watch-gate

This is the app's central mechanic and it is enforced **client-side**. The relay
does not enforce policy; it has no idea what a payload means.

```
Viewer (has map open)                Sharer (owns the location)
  |                                       |
  |-- watch{on:true} --> relay -----------|
  |                                       | grant lease, ttl = LEASE_TTL (60s)
  |                                       | START streaming LOC payloads
  |                                       |
  |<-- roster{watching:true} --------------|  (all members see the watch state)
  |                                       |
  |   (user moves)                        | LOC payload every UPLOAD_INTERVAL
  |<------- sealed LOC payloads ----------|
  |                                       |
  |                                       | renew lease every 30s
  |                                       |
  |  (user leaves / socket dies)          |
  |-- watch{on:false} / disconnect ------>|
  |                                       | STOP after GRACE_SEC (20s)
```

Two ways to become a watcher:

1. **Passive** — the map screen is in the foreground. The client sends
   `watch{on:true}` on resume and `watch{on:false}` on pause.
2. **Active ("acquire live location")** — the `pull` button asks one member
   directly for a bounded window, independent of whether that member's map is
   open. The target shows a visible "sharing" indicator and the countdown.

A device streams only while **at least one** peer has `watching == true`, or while
an unexpired `pull` lease is held. Otherwise it transmits nothing — no heartbeats,
no position, nothing. This is what makes the app battery-acceptable.

## 8. Payload types

The sealed plaintext is JSON. `type` is bound into the signature, so a signed
`LOC` cannot be reinterpreted as something else.

### `LOC` — a position fix

```jsonc
{
  "type": "LOC", "seq": 42, "ts": 1712345678901,
  "lat": 52.520008, "lon": 13.404954,
  "acc": 12.5,          // horizontal accuracy, metres
  "alt": 34.0,          // metres, nullable
  "spd": 1.4,           // m/s, nullable
  "brg": 87.0,          // degrees, nullable
  "bat": 0.63,          // 0..1, nullable
  "src": "gps"          // gps | network | fused | manual
}
```

Coordinates are sent at full precision. Optional obfuscation for a future
"approximate location" mode is *not* implemented in v1; see §11.

### `FENC` — a geofence transition

Emitted by each device about **itself only**, evaluated locally, so alerts fire
without depending on anyone else watching.

```jsonc
{
  "type": "FENC", "seq": 43, "ts": 1712345678901,
  "fid": "<geofenceId>", "ev": "enter" | "exit",
  "lat": 52.52, "lon": 13.40
}
```

### `MEM` — profile change (display name, colour)

```jsonc
{ "type": "MEM", "seq": 44, "ts": 1712345678901, "name": "Ana", "color": "#e11d48" }
```

## 9. Geofence evaluation

Geofences are stored per-device and evaluated by the device owner, locally, on
every fix — independently of the watch-gate. Two consequences worth stating:

- **Self** enter/exit is detected and notified **always**, with zero network use.
- **Others'** enter/exit is detected on *their* phone. If nobody was watching when
  it happened, the event is queued and flushed to the group the next time a
  watcher connects, timestamped as the original occurrence time.

This is why geofence alerts survive the watch-gate without weakening it.

### Shapes

- `circle` — `{ "lat":…, "lon":…, "m": 120 }`, haversine distance ≤ `m`.
- `polygon` — `{ "ring": [[lat,lon], …] }`, even-odd ray casting, exactly as
  both platforms implement it. Winding order is irrelevant.

### Per-fence notification switches

| Field | Meaning |
|---|---|
| `notifyEnter` | Notify when **any** member enters. |
| `notifyExit` | Notify when **any** member leaves. |
| `notifySelf` | Notify me about **my own** transitions. Independent of the two above. |
| `notifyOthers` | Notify me about **other members'** transitions. |

Self transitions are evaluated locally and never require `notifyOthers`.

## 10. Timing and constants

| Constant | Value | Rationale |
|---|---|---|
| `UPLOAD_INTERVAL` | 4 s while streaming | Smooth enough to look live |
| `LEASE_TTL` | 60 s | Renewed at 30 s |
| `GRACE_SEC` | 20 s | Absorbs map open/close churn and flaky mobile links |
| `MAX_SKEW_MS` | 600 000 | Reject payloads older than 10 min |
| `STALE_AFTER_MS` | 30 000 | Grey out a member's marker; keep the last fix |
| `PULL_DEFAULT_TTL` | 900 s | 15 minutes for the "get live location" button |
| `MAX_FRAME_BYTES` | 16 384 | Hard cap; relay drops oversize frames |
| `HEARTBEAT_SEC` | 25 s | Detects dead sockets on the relay |

## 11. Known limitations of v1

Stated plainly rather than implied.

1. **No forward secrecy.** The group key is long-lived. Anyone who obtains it can
   decrypt stored traffic. Signal's Double Ratchet is not implemented.
2. **No retroactive revocation.** Group-key rotation stops future decryption only.
   Real per-member revocation needs `x25519` key wrapping, which the format in §3
   reserves but v1 does not fully use.
3. **Metadata is visible.** The relay learns which device is in which group, when
   each is online, and who is watching. It does **not** learn coordinates. This is
   the same exposure model as Signal's service.
4. **No authentication on the relay.** Possession of `groupId` is sufficient to
   join and to observe roster metadata. Adding an invite-issued capability token
   would close this and is the highest-value next change.
5. **Clock trust.** `ts` is sender-supplied. A device with a wrong clock can pin a
   stale position. `seq` limits replay within a session but cannot fix a bad clock.
6. **No location obfuscation.** Full-precision coordinates only.
7. **Single process, no multi-device.** One phone is one device; linking a second
   is not implemented.
8. **iOS background limits.** iOS will not let an app stream continuously in the
   background. The foreground app streams normally; background behaviour degrades to
   occasional `CLLocation` callbacks. Android's foreground service has no such cap.
   **The two platforms are therefore not symmetric**, and this is imposed by the OS.

## 12. Conformance

`relay/test_protocol.py` exercises the relay against a reference implementation of
§4–§6. When adding a platform, port `test_protocol.py`'s vectors first and make
them pass before writing UI.
